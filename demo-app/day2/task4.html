Secure Retrieval, Three Roles

Retrieve-then-filter is not access control. The restricted content already entered the model's context and shaped the answer — the clean citations are a hope, not a control. Get this one wrong and every other control you built today is decoration.

The scenario & the three roles

One corpus, three roles, and a rule that has to hold every time. The user's access rights must become part of the retrieval query, so restricted documents are never candidates and cannot influence anything.

RoleMay accessMust not access
Service engineerMaintenance procedures, troubleshooting guides, parts catalogues for certified familiesDesign documents, unreleased specs, commercial terms, other customers' records
Product engineerDesign documents, specifications, test reports, failure analysesCustomer-specific commercial data, personal data in service records
Customer supportPublished documentation, warranty terms, the requesting customer's own service historyInternal engineering documents, other customers' data, cost and margin information

What the attendees must build

  • Retrieve-then-filter and filter-then-retrieve both demonstrated, on the same leaking question
  • Access metadata on every chunk — not every document — and a filter predicate applied inside the search call
  • Identity propagation: the authenticated identity from Task 2 reaches the retrieval layer, not a service account
  • The empty path — “nothing available to you” handled gracefully as a correct answer
  • Six automated tests minimum, three of them negative (must return nothing)
  • Three role-scoped evaluation scores, reported separately
  • All four leakage paths checked, with the log and trace stores actually grepped
  • Red-team findings reported for the system you attacked and for your own

The librarian

A librarian who fetches every book, reads them, summarises them and then tries not to mention the restricted ones has already read the restricted ones to you, in aggregate. A librarian who only searches the shelves you are permitted to use has not. Only the second is access control — and it is the difference between the two designs above.

The path this room fails

Observability systems store full prompts and responses by default — that is what makes them useful. Your Task 2 trace log almost certainly contains restricted document text in plain text, readable by anyone with log access, retained for weeks. The fix: store the document ids rather than the passages, and a hash rather than the text. Access control at retrieval is worthless if the trace store hands the same text to anyone who can read the logs.

The lesson this build makes undeniable

Access control belongs inside the retrieval query. Filtering the output is not access control.

A document the user may not see must never become a candidate, because once it enters the model's context it has already shaped the answer — and no citation filter can un-shape it. The negative tests prove the control works; the trace-store audit proves it holds all the way to where the text is stored.

Defend your result

“Our naive design answered a restricted question with clean citations; our filtered design refuses it. Our gold set scores 0.78 / 0.85 / 0.62 for the three roles. We found 3 leaks in the system we attacked and 1 in our own — the one that surprised us was the trace store, which kept restricted passages in plain text weeks after retrieval had correctly refused them.”
