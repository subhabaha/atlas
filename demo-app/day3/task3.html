Three MCP Servers

A vague tool description causes wrong calls that look exactly like a model reasoning problem — so teams change the model, and the problem persists. And identity has to reach the server: if the server trusts the client, one credential leaks data no logs flag. Two failures, neither of them a model failure.

The scenario

A knowledge assistant that retrieves technical documents, queries a service-ticket store and calls a diagnostic lookup. Three capabilities, owned by three different teams in real life, built here as three MCP servers over stdio — small self-contained processes backed by SQLite or JSON, because the point is the contract, not the storage.

The arithmetic to lead with: five AI applications across eight enterprise systems is forty bespoke integrations — each with its own auth, error semantics, versioning and security review. Or eight governed servers, each built and reviewed once, consumed by any client. MCP turns integration from an application concern into a platform concern.

A wrong call that looks like a model failure

With a vague description, requests for ticket history get routed to search_documents because the name alone looked plausible. It reads as a reasoning error — so teams change the model, and the accuracy does not move. Toggle the rewrite to see where the number goes.

The authorisation boundary — the confused deputy
The same low-privilege request (viewer role asks for a restricted maintenance-cost field). One design leaks it; the other refuses it.

Tool authorisation derives from who the caller is, never from what the model read. If retrieved content could cause a tool to be invoked with authority the caller does not have, the boundary is in the wrong place. The remaining four controls: per-role allow-lists enforced outside the model, full call logging, idempotency on state-changing calls, and an approval gate on anything irreversible.

Four cases × three servers. A tool that raises an exception leaves the model with nothing usable and it will improvise. Every cell returns a defined, typed response instead.

Not everything should be a tool

retrieve-context, the pre-generation retrieval step, should not be an MCP tool. The model never decides whether it runs — it always runs before generation. That makes it a pipeline stage; wrapping it in MCP adds latency and indirection for nothing. Use MCP when the model chooses at runtime.

The trap that looks like a model problem

The vague description

“Searches the document store using the retrieval component.” It describes the implementation, offers no “when not to use”, and no examples. The model infers usage from the name and calls it for ticket questions too. Selection accuracy sits at 63% — and every retry with a stronger model leaves it there.

The confused deputy

The server holds one high-privilege credential and trusts the client to have checked. A low-privilege caller asks a question; the server executes with its own high privilege and returns data the caller may not see. Nothing in the logs looks unusual. This is very easily introduced and it is the classic vulnerability of the architecture.

Write the description twice

Once for the implementer, once for a competent new colleague who has never seen the system. That second reader is exactly who your tool description has — except it will never ask a clarifying question. Compare which version the model actually uses correctly.

The lesson this build makes undeniable

A tool contract is an interface, and identity is part of it.

The description is written for a model, not a human, and it is the least-discussed cause of agent failure — your before-and-after numbers turn that from an opinion into evidence. And authorisation belongs at the server, deciding from who the caller is, never from what the model read.

Defend your result

“Vague descriptions gave 63% tool-selection accuracy; rewritten ones gave 94%. We changed no model and no prompt. Our confused-deputy demonstration returned restricted cost data before identity propagation and a refusal after. The tool we decided should not be a tool is retrieve-context — the model never chooses whether it runs.”
